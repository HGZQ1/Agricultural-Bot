# 农业番茄采摘机器人仿真项目需求与技术方案

> 文档状态：需求基线草案 v0.1  
> 目标平台：Ubuntu 24.04 LTS + ROS 2 Jazzy + Gazebo Harmonic  
> 最后核对：2026-10-03  
> 本阶段范围：完整仿真闭环，不包含真实机器人部署与安全认证

## 1. 项目目标

在 Gazebo Harmonic 中建立一套可重复运行的温室番茄采摘仿真案例。机器人由方形四轮移动底盘、越疆 CR5 六轴机械臂、开合夹爪、腕部 RealSense D405 深度相机、Livox MID-360 激光雷达和车载固定篮筐组成。

系统需完成以下闭环：

1. 在平行土槽和通行道路构成的温室中自主建图。
2. 基于已保存地图完成定位、自主规划、避障和行间通行。
3. 到达采摘作业点后停车并锁定底盘。
4. 机械臂携带 D405 扫描植株，YOLOv8 识别成熟番茄。
5. 结合对齐深度图和 TF 计算番茄三维位置。
6. 规划机械臂接近、夹取、撤离和投放动作。
7. 将番茄放入车载固定篮筐，并继续下一个目标。

项目最终应提供一条命令启动的全栈演示、分模块调试入口、可复现测试场景、运行日志及验收结果。

### 1.1 最终正常运行流程

最终系统分为“首次建图”和“日常采摘”两条流程。温室布局未变化时，不应每次采摘都重新建图；只有首次部署、土槽布局明显变化或原地图失效时才重新执行建图流程。

#### A. 首次部署或场景变化：自动建图

目标启动方式：

```bash
ros2 launch agri_bringup simulation.launch.py \
  mode:=mapping \
  world:=greenhouse_default.sdf \
  map_name:=greenhouse_map
```

运行步骤：

1. Gazebo 加载温室和机器人，机械臂进入 `arm_stow` 收纳姿态，夹爪保持闭合或安全开度。
2. 系统启动底盘控制、MID-360 等效点云、里程计、可选 IMU、EKF、SLAM Toolbox 和 Nav2 建图模式。
3. 启动检查确认 `/clock`、TF、`/odom`、`/scan` 和控制器正常；任一关键接口超时则不允许底盘运动。
4. 覆盖路线执行器根据温室行列拓扑生成蛇形航点，机器人自动依次进入各条道路和行末调头区。
5. 行驶过程中，SLAM Toolbox 持续建立占据栅格；Nav2 根据在线地图和 MID-360 障碍物数据规划并避障。
6. 单个航点不可达时，系统执行清障等待、重新规划和有限次恢复；仍不可达则记录并继续其他可达区域。
7. 全部覆盖航点完成后，系统检查道路覆盖率、地图连通性和回环状态，自动保存地图 YAML/PGM、轨迹和建图报告。
8. 建图完成后底盘返回 `home_pose`，机械臂保持收纳，任务进入 `MAPPING_COMPLETED`。地图验收通过后才能用于日常采摘。

#### B. 日常作业：自动采摘

目标启动方式：

```bash
ros2 launch agri_bringup demo.launch.py \
  map:=greenhouse_map.yaml \
  mission:=harvest_default.yaml \
  autostart:=true
```

`harvest_default.yaml` 至少定义地图、`home_pose`、扫描站点顺序、每个站点的机械臂扫描姿态、最大采摘数量/软件篮筐计数上限、任务超时和任务结束后是否返航。软件计数仅表示本次任务成功入篮数量，不等同于真实篮筐满载检测。

正常运行时序：

```text
启动与自检
  -> AMCL 定位
  -> 导航到扫描站点
  -> 锁定底盘
  -> 机械臂多姿态扫描
  -> YOLOv8 成熟果识别
  -> 深度融合与 6D 抓取候选生成
  -> MoveIt 2 规划并抓取
  -> 放置到车载篮筐
  -> 同站点下一目标 / 下一扫描站点
  -> 返回 home_pose
  -> 保存报告并结束
```

详细步骤：

1. **启动与自检**：`demo.launch.py` 依次启动 Gazebo、控制器、传感器桥接、robot state publisher、EKF、map server、AMCL、Nav2、MoveIt 2、YOLOv8 感知和任务管理器。所有必需 lifecycle 节点 active 后才进入 `READY`。
2. **定位**：系统加载已保存地图，在 `home_pose` 附近完成 AMCL 初始定位。定位协方差或 TF 不满足阈值时，任务保持暂停，不发送导航或机械臂命令。
3. **任务装载**：任务管理器读取扫描站点，清空本次运行的目标跟踪表和篮筐软件计数，确认机械臂处于 `arm_stow`。
4. **自主导航**：Nav2 将机器人送到下一扫描站点。MID-360 同时用于定位和障碍物更新；遇到临时障碍时减速、等待或重新规划。
5. **底盘互锁**：到达站点后取消导航目标，启用 `twist_mux` lock 并等待底盘持续静止。互锁未成立时，机械臂不得展开。
6. **植株扫描**：CR5 按 `arm_scan_1 ... arm_scan_n` 观察姿态移动，D405 在 0.10-0.50 m 工作距离内采集对齐 RGB-D 数据。
7. **识别与定位**：YOLOv8-seg 区分成熟和未成熟番茄；感知节点融合实例掩码、深度和 TF，生成稳定 `track_id`、果心、半径、法向和抓取姿态候选。
8. **目标选择**：系统过滤未成熟、已采摘、深度无效、被严重遮挡和不可达目标，再按置信度、可达性、碰撞风险和运动代价选择一个成熟果。
9. **抓取**：MoveIt 2 规划到预抓取位，机械臂直线接近，夹爪闭合。仿真端确认距离/接触条件后将目标状态从 `ON_PLANT` 更新为 `ATTACHED_TO_TOOL`。
10. **撤离与入篮**：机械臂沿安全方向撤离，移动到 `basket_drop_pose`，打开夹爪。番茄在篮筐判定区域稳定后更新为 `IN_BASKET`，软件计数加一。
11. **站点循环**：若当前站点仍有可采成熟果，则重新扫描并抓取；否则机械臂回到 `arm_stow`，解除底盘锁定并导航到下一站点。
12. **全局循环**：依次完成任务文件中的全部扫描站点，直到达到目标数量/软件篮筐计数上限、所有站点处理完成、任务超时或收到取消请求。
13. **安全收尾**：停止生成新抓取任务。若夹爪仍持有果实，优先完成当前安全放置；随后夹爪回到安全开度、机械臂进入 `arm_stow`，才能解除底盘互锁。
14. **返航结束**：正常完成后底盘返回 `home_pose` 并停止。系统保存采摘数量、漏采/失败目标、导航恢复次数、耗时、轨迹、指标 JSON 和 rosbag2，状态进入 `COMPLETED`。

操作者界面至少显示当前运行模式、站点、`track_id`、任务阶段、成功/失败/跳过计数和最近故障原因，并提供开始、暂停、继续、跳过目标、跳过站点、取消和返回 `home_pose` 命令。暂停不得在不安全的轨迹中间直接切断执行，应先停止生成新动作，并在到达最近安全保持点后进入 `PAUSED`。

#### C. 无目标和异常时的行为

- 扫描站点没有成熟果：记录 `NO_RIPE_TARGET`，收臂后直接前往下一站点，不视为系统故障。
- 目标瞬时丢失或深度无效：改变观察姿态并重新扫描，最多重试 2 次；仍失败则跳过该目标。
- IK、碰撞检查或运动规划失败：尝试下一抓取候选；全部失败则标记 `UNREACHABLE`。
- 抓取或入篮失败：退回安全位重新识别，最多重试 2 次；果实掉落必须记录为失败，不得计入篮筐数量。
- 导航失败：依次执行等待、重新规划和 Nav2 恢复；站点仍不可达时跳过并记录。
- 定位丢失、TF 断裂、控制器失活、底盘在抓取时移动或发生禁止碰撞：立即停止底盘和机械臂，保持或返回可达的安全姿态，状态进入 `SAFE_STOP`，等待人工确认，不自动继续任务。
- 操作者取消：停止生成新 action；若夹爪持果且安全路径可用，先放入篮筐，否则保持当前位置并进入安全停止。机械臂在可行时回到收纳位，底盘不再前往新站点，保存部分任务报告并进入 `CANCELED`。

正常无故障时，操作者只需启动并监控任务；必要时可暂停、继续、跳过、取消或要求返航，不需要逐个发送导航点、手动选择番茄或遥控机械臂。

## 2. 范围与边界

### 2.1 本阶段必须完成

- 机器人完整 URDF/Xacro、碰撞模型、惯性参数和 TF 树。
- 温室、土槽、道路、植株、番茄和篮筐的 Gazebo 世界。
- 四轮底盘、CR5 和夹爪的仿真控制。
- MID-360 等效三维点云和 D405 等效 RGB-D 数据输出。
- 2D 自主建图、地图保存、AMCL 定位和 Nav2 自主导航；建图过程中不依赖人工遥控完成行间覆盖。
- YOLOv8 番茄识别、深度融合、三维目标定位和目标去重。
- MoveIt 2 机械臂运动规划、碰撞检查、抓取和放置。
- 多站点、多番茄的完整“搜索-采摘-入篮”任务闭环。
- RViz2 可视化、rosbag2 记录、自动化测试和使用文档。

### 2.2 本阶段不包含

- 真实底盘、电机驱动器、CR5、MID-360、D405 的硬件联调。
- 真实温室中的防水、防尘、线缆、供电、急停和功能安全认证。
- 底盘与机械臂同时运动的全身运动规划。基线方案规定采摘时底盘静止。
- 茎秆切割、果梗识别、力控柔顺采摘和果实损伤评估。
- 自动充电、篮筐满载检测、跨楼层或室外导航。

### 2.3 关键假设

- 当前 `robot_pick_robot11` URDF 已确认底盘为四舵轮：每个轮组包含独立转向关节和驱动关节。本阶段尺寸、安装位姿和网格变换以该 URDF 为准；旧版图纸中的轴距、轮距、轮胎和外廓数值只作历史参考，不作为当前验收基线。机械转向限位、零位偏置、减速比和最大速度仍待硬件确认。
- 仿真首先建立稳定的功能等效传感器接口，不追求逐激光束、逐曝光完全复刻真机。
- CR5 型号暂按传统 CR5，而不是 CR5A/CR5AF。实机型号和控制器协议版本需要在硬件迁移前确认。
- 番茄采摘对象分为 `ripe_tomato` 和 `unripe_tomato`；任务只采摘成熟番茄。
- D405 是近距离相机，基线流程不依赖其远距离发现番茄，而是在预设行间扫描点由机械臂执行腕部相机扫描。
- 首版“自主建图”指在已知温室行列拓扑下自动执行覆盖路线，但 SLAM 不读取 Gazebo 真值位姿或真值地图；若要求对完全未知布局自主探索，需启用后续的前沿探索增强项。

## 3. 机器人与场景需求

### 3.1 机器人组成

| 子系统 | 仿真要求 | 当前输入/约束 |
| --- | --- | --- |
| 移动底盘 | 四舵轮，支持转向角与轮速独立控制并输出里程计 | 以 `robot_pick_robot11` 当前 URDF 的尺寸、安装位姿和网格为准；转向限位和整车质量待确认 |
| 机械臂 | 越疆 CR5，6 自由度，支持关节轨迹控制 | 额定负载 5 kg、工作半径 900 mm、本体约 25 kg；末端工具总质量计入负载 |
| 夹爪 | 两指开合，支持开/闭和位置控制 | 型号、行程、最大开口、质量、指尖尺寸待确认 |
| 腕部相机 | D405 等效彩色图、深度图、CameraInfo | 理想工作距离约 0.07-0.50 m，适合近距离抓取定位 |
| 主激光雷达 | MID-360 等效 3D 点云 | 360° 水平视场、约 59° 垂直视场、典型 10 Hz |
| 篮筐 | 固连于底盘，具有视觉和碰撞模型 | 安装位置、内部尺寸和容量待确认 |

机械设计必须校核：

- CR5、夹爪、相机、支架和果实的质量及惯性。
- 机械臂最大伸展时整车重心和抗倾覆稳定性。
- 机械臂、相机、篮筐、雷达之间的自碰撞。
- CR5 末端 5 kg 额定负载中夹爪、相机、支架和目标物的总质量余量。
- 相机视线不被夹爪手指或安装板长期遮挡。

### 3.2 温室场景

温室世界应参数化生成，至少包含：

- 平整地面、温室骨架/围挡、入口和边界。
- 多个平行长方形土槽，土槽之间形成可通行道路。
- 行末调头区，以及能够容纳机器人外接矩形安全转弯的空间。
- 番茄植株、叶片、枝干、成熟和未成熟果实。
- 固定障碍物和可选动态行人，用于导航避障测试。
- 可配置灯光、阴影、纹理、果实大小、遮挡程度和随机种子。

首版可采用下列占位参数，最终值必须根据底盘实际尺寸修订：

| 参数 | 首版建议值 | 配置位置 |
| --- | --- | --- |
| 世界尺寸 | 20 m x 12 m | `greenhouse.yaml` |
| 土槽数量 | 4 | `greenhouse.yaml` |
| 单个土槽 | 8 m x 1 m x 0.35 m | `greenhouse.yaml` |
| 行间道路宽度 | 1.5 m | `greenhouse.yaml` |
| 行末调头区 | 2.0 m | `greenhouse.yaml` |
| 番茄直径 | 60-90 mm 随机 | `tomato_assets.yaml` |

道路宽度的最终约束为：机械臂处于收纳姿态时整机外接宽度 + 两侧安全余量，并需要覆盖 Nav2 膨胀层。整机包络包括底盘、篮筐、收拢机械臂/夹爪和突出传感器，不能只按底盘视觉宽度布置场景。

标准端到端验收场景暂定为 2 条行间道路、3 个扫描站点、6 个可达成熟番茄和不少于 3 个未成熟干扰目标。单次任务成功必须同时满足：在 12 分钟仿真时间内采摘并入篮不少于 5 个成熟果、误采未成熟果为 0、掉落为 0、禁止接触碰撞为 0。实际温室和底盘尺寸确认后再冻结该规模。

### 3.3 番茄交互模型

采摘仿真分两级实现：

1. **功能级（项目基线）**：夹爪 TCP 进入阈值范围、目标位姿有效且夹爪闭合后，通过仿真服务将番茄刚性附着到夹爪；打开夹爪后解除附着。该方式用于稳定验证任务逻辑。
2. **物理级（增强项）**：使用接触、摩擦、可断开果梗关节和重力模拟真实夹持。该方式易受碰撞网格和物理参数影响，不作为首个闭环的前置条件。

每个番茄必须具有唯一 ID、成熟状态、世界真值位姿、是否已采摘状态和可碰撞几何体。真值仅供评测，不得直接作为识别节点输入。

果实在仿真内部按以下状态机管理：

```text
ON_PLANT -> ATTACHED_TO_TOOL -> IN_BASKET
                            -> DROPPED
```

- `ON_PLANT -> ATTACHED_TO_TOOL`：夹爪闭合、TCP/接触距离满足阈值且附着服务成功，同时移除或断开果梗约束。
- `ATTACHED_TO_TOOL -> IN_BASKET`：夹爪打开、解除附着，果实稳定进入篮筐内部判定区域。
- `ATTACHED_TO_TOOL -> DROPPED`：解除附着后未进入篮筐区域，或在运输中脱落。
- 感知节点自行生成不透明的 `track_id`，不得使用 Gazebo entity ID 或模型名称。仿真附着插件根据“估计目标位姿 + TCP/接触几何 + 最近的 `ON_PLANT` 果实”完成内部关联，entity ID 只保留在仿真和评测层。

## 4. 功能需求与验收条件

| 编号 | 功能需求 | 验收条件 |
| --- | --- | --- |
| FR-01 | 一键启动 | `ros2 launch agri_bringup demo.launch.py` 启动 Gazebo、机器人、控制器、桥接、Nav2、MoveIt 2、感知、任务管理器和 RViz，并自动开始标准场景；无必需节点异常退出 |
| FR-02 | 机器人模型 | RViz/Gazebo 中关节、轮子、夹爪、相机、雷达和篮筐位置正确；`check_urdf` 通过；无断裂 TF |
| FR-03 | 底盘控制 | 接收 `/cmd_vel`，前进、后退、原地转向正常；停止指令后无持续漂移 |
| FR-04 | 机械臂控制 | `FollowJointTrajectory` 可执行 CR5 轨迹；夹爪 action 可开合；关节限制有效 |
| FR-05 | 传感器接口 | 发布带正确时间戳和 frame ID 的点云、彩色图、深度图、CameraInfo；RViz 可显示 |
| FR-06 | 自主建图 | 使用 MID-360 等效数据自动遍历全部可通行行间，生成并保存完整 2D 占据栅格；无需人工遥控，主要道路连通、墙体/土槽边界无明显重影 |
| FR-07 | 定位与导航 | 在已保存地图上完成 AMCL 定位和 Nav2 导航；10 个固定目标点至少成功 9 次且无碰撞 |
| FR-08 | 番茄识别 | 在标准仿真测试集上区分成熟/未成熟番茄；成熟番茄检测 Precision、Recall 均不低于 0.90（初始目标） |
| FR-09 | 三维定位 | 将目标从像素坐标转换到当前 `base_link`（后续可增加语义 `arm_base_link`）；可见且深度有效时位置中位误差不高于 30 mm |
| FR-10 | 抓取规划 | MoveIt 2 生成无碰撞的预抓取、直线接近、闭合、撤离轨迹；超出工作空间的目标被拒绝 |
| FR-11 | 放置入篮 | 番茄从夹爪释放后落入篮筐内部，任务状态更新且不重复采摘 |
| FR-12 | 任务闭环 | 在已保存地图上，从初始位姿开始完成“定位-导航-扫描-识别-抓取-放置入篮”；标准场景的 10 次固定随机种子测试至少成功 8 次 |
| FR-13 | 故障恢复 | 目标丢失、深度无效、规划失败或抓取失败时执行有限次重试，并能跳过目标或安全回到收纳姿态 |
| FR-14 | 可观测与任务控制 | 可查看 TF、地图、代价地图、路径、点云、检测结果、目标位姿、规划场景和任务状态；可执行开始、暂停/继续、跳过、取消和返航；关键流程可录制 rosbag2 |

上述数值是首版验收基线。底盘尺寸、GPU 性能和场景难度确定后，可在不降低安全约束的前提下修订。

## 5. 非功能需求

- 所有节点统一使用仿真时钟，设置 `use_sim_time: true`。
- 配置参数进入 YAML/Xacro，不在节点中硬编码世界尺寸、关节名、话题名和阈值。
- 传感器流使用 `SensorDataQoS`；控制 action/service 使用可靠 QoS。
- 资源命名、TF、话题和 action 保持稳定，并在接口文档中登记。
- 使用固定随机种子时，测试场景和结果应可复现。
- 高带宽图像和点云只做单向 `GZ_TO_ROS` 桥接，避免回环和不必要的复制。
- 仿真 GUI 与算法可分离运行；持续集成采用无界面模式。
- 所有我方自研 ROS 2 可执行节点、适配器、感知和任务逻辑均使用 Python 3.12、`rclpy` 和 `ament_python`，通过 Ruff/pytest/launch_testing；C++ 仅作为未修改的官方底层依赖或固定版本、经许可证审核的第三方底层依赖存在，边界见 7.2。
- 大型网格、纹理、权重和数据集使用 Git LFS 或独立下载脚本，不直接混入普通 Git 历史。
- 第三方依赖必须锁定版本或提交 SHA，并登记许可证。Ultralytics 当前开源许可为 AGPL-3.0；若项目闭源或商用，必须先完成许可证评估。

### 6.1 作业状态机

```text
INIT -> LOCALIZE -> NAVIGATE_TO_SCAN_POSE -> LOCK_BASE
  -> SCAN_ARM -> DETECT -> ESTIMATE_3D -> SELECT_TARGET
  -> APPROACH -> GRASP -> RETREAT -> PLACE_IN_BASKET -> STOW_ARM
  -> NEXT_SCAN_POSE_OR_FINISH

DETECT / ESTIMATE_3D / APPROACH / GRASP
  -> bounded retry -> skip target or safe stop
```

约束：进入 `LOCK_BASE` 后取消 Nav2 目标、发布零速度并确认底盘静止；机械臂回到收纳姿态后才允许底盘继续移动。

### 6.2 坐标系约定

必须遵循 REP-103/REP-105，建议 TF 树如下：

```text
map
└── odom
    └── base_footprint
        └── base_link
            ├── wheel_*_link
            ├── mid360_link
            │   └── mid360_sensor_frame  (无质量固定扫描 frame)
            ├── tomato_box_link  (目标语义名：basket_link)
            └── arm_link1       (目标语义名：arm_base_link)
                └── ... CR5 links ...
                    └── tool0
                        └── gripper_base_link
                            ├── gripper_left_finger_link
                            ├── gripper_right_finger_link
                            └── camera_link  (目标语义名：d405_link)
                                └── camera_lens_link  (保留 CAD 壳体)
                                    └── d405_sensor_frame  (无质量投影 frame)
                                        └── camera_optical_frame
```

- `map -> odom` 只由 SLAM Toolbox 或 AMCL 发布。
- `odom -> base_footprint` 只允许一个发布源。使用 EKF 时，应关闭底盘控制器对应 TF 发布，避免双发布。
- 所有网格单位使用米、千克、弧度；相机 optical frame 使用 ROS 光学坐标约定。
- 仿真中的相机外参来自 URDF 固定关节；迁移实机时必须执行眼在手上的手眼标定。

`HarvestMission` goal 至少包含 mission ID、地图/路线配置标识和是否返航；feedback 包含当前状态、站点、目标和进度；result 包含终态、成功/失败/跳过计数、耗时和报告路径。`MissionCommand` 使用固定枚举 `PAUSE`、`RESUME`、`SKIP_TARGET`、`SKIP_STATION`、`RETURN_HOME`，不接受任意命令字符串。

自定义检测消息至少包含：时间戳、目标 ID、类别、置信度、2D 框或掩码、相机坐标系三维点、目标坐标系三维位姿、深度有效率和状态。

`AttachTomato` 请求包含感知 `track_id`、估计目标位姿和 tool link；仿真插件只返回成功/失败与原因，不向感知节点返回 Gazebo entity ID。插件内部保存本次附着关联，`DetachTomato` 使用 `track_id`/tool link 解除同一实体。评测节点可在内部维护 `track_id <-> entity_id` 对照，但不得发布给算法节点。

传感器数据契约：

- D405 等效流固定为 848 x 480、30 Hz；彩色输入接受 `rgb8`/`bgr8` 并在节点入口统一为 BGR。
- 深度输入必须兼容 `16UC1`（毫米，RealSense 常见输出）和 `32FC1`（米，Gazebo 常见输出），入口统一转为以米为单位的 `float32`；0、NaN 和 Inf 均视为无效值。
- 当前原生 Gazebo 适配在 sim_ws 将 CameraInfo K/P 主点由渲染的 `(424,240)` 校正为 ROS 整数像素中心的 `(423.5,239.5)`，保留时间戳、frame 与焦距。算法按标准整数像素反投影；实机 RealSense 不叠加该半像素校正。
- 彩色、深度和 CameraInfo 的分辨率及 optical frame 必须一致；近似同步最大时间差 33 ms，TF 等待上限 100 ms。默认近距抓取工作距离为 0.10-0.50 m；仿真可选 0.07-2.00 m 扩展 profile，后续感知距离过滤上下限必须参数化，远距粗定位与近距抓取分别配置。
- MID-360 等效点云固定 10 Hz、水平 360°、垂直 `-7° 到 +52°`、最小量程 0.1 m、等效最大量程 40 m。垂直角按 `mid360_sensor_frame` 的局部轴向定义；该扫描 frame 相对 `base_footprint` 的安装俯仰为 −15°。保留 `mid360_link` 的 CAD 网格轴与外观位姿，不重复旋转网格，禁止将局部垂直范围配置为对称的 ±29.5°。
- MID-360 仿真仅承诺标准 `PointCloud2` 的 `x/y/z/intensity`；非重复扫描线、逐点时间戳和 Livox 自定义字段不属于首版接口。

### 6.4 运行模式

建图与定位不能同时发布 `map -> odom`。顶层 launch 必须通过 `mode` 参数互斥启动：

| 模式 | 启动组件 | 目的 |
| --- | --- | --- |
| `mapping` | SLAM Toolbox、使用在线 `/map` 的完整 Nav2 导航栈、自动覆盖路线执行器 | 自动遍历行间并保存地图，不启动 map server/AMCL |
| `navigation` | map server、AMCL、Nav2 | 在保存地图上进行导航调试，不启动 SLAM |
| `harvest` | `navigation` 全部组件 + 感知、MoveIt 2、任务管理器 | 执行完整采摘任务 |

首版自动建图根据 `greenhouse.yaml` 生成蛇形行间覆盖航点，并通过 Nav2 逐点执行；不得读取 Gazebo 真值位姿。建图模式设置规划器 `allow_unknown: true`，但每次只下发当前点云已确认可接近的下一段航点，并由局部代价地图/碰撞监控兜底。路线完成后自动调用地图保存服务。未知布局的前沿探索作为增强项，不作为首个闭环的依赖。

## 8. 关键技术方案

### 8.1 SolidWorks 模型转 ROS/Gazebo 模型

1. 清理装配体，按实际运动副拆分底盘、车轮、机械臂安装座、篮筐、夹爪等刚体。
2. 从 SolidWorks 导出 STEP 作为几何基准；每个刚体另导出 STL/DAE，统一米制和坐标方向。
3. 视觉网格保留必要外观，碰撞网格使用凸包或基础几何体，避免直接使用高面数三角网格碰撞。
4. 根据 CAD 质量属性填写每个 link 的质量、质心和惯性矩阵，不使用全零或任意惯性。
5. 使用 Xacro 分为底盘、CR5、夹爪、相机、雷达和篮筐模块，安装位姿通过参数传入。
6. 依次通过 `check_urdf`、RViz 静态检查和 Gazebo 重力/碰撞检查。

SolidWorks URDF 导出结果只能作为初稿，必须人工检查 joint 轴、limit、origin、mesh scale、惯性和闭环结构。

### 8.2 四舵轮底盘与里程计

- 使用 Python `agri_base_kinematics` 节点接收经 `agri_base_adapter` 门控后的
  `geometry_msgs/msg/TwistStamped`，根据四个轮心坐标计算各转向角和驱动轮角速度；
  手动输入使用 `/cmd_vel`，导航输入使用 `/cmd_vel_nav`，最终唯一出口为
  `/cmd_vel_safe`。
- 四个转向关节使用位置命令接口，四个驱动轮使用速度命令接口；底层由标准 `ros2_control` forward controllers 执行，不使用 `diff_drive_controller`。
- 逆运动学基线为 `v_ix = vx - wz*y_i`、`v_iy = vy + wz*x_i`、`delta_i = atan2(v_iy, v_ix)`、`omega_i = hypot(v_ix, v_iy)/R`，并实现“转向角加减 π + 轮速反向”的最短转向优化。
- 转向限位未确认前，仅验收直行和限位内转弯；横移、斜行和原地旋转作为条件能力，不得写入必过验收。
- 所有发布/转发速度的 Nav2 节点统一设置 `enable_stamped_cmd_vel: true`，禁止在同名话题混用 `Twist` 与 `TwistStamped`。
- 使用唯一的 `joint_state_broadcaster/JointStateBroadcaster` 发布整机 `/joint_states`，再由 `robot_state_publisher` 生成关节 TF；运行控制器时不得同时启动 GUI 假关节状态发布器。
- Python 底盘里程计节点根据转向/轮速反馈估计 `/wheel/odom`，由
  `agri_base_adapter` 校验并发布标准 `/odom`；阶段一由四舵轮节点独占
  `odom -> base_footprint` TF，启用 `robot_localization` 融合轮式里程计和可选 IMU
  后，必须关闭该 TF 发布再由 EKF 独占。
- 配置已确认的轮半径、轮距、轴距和速度/加速度限制，以及覆盖机械臂收纳状态整机包络的多边形 footprint。
- 在不同地面摩擦系数下测试直行、转弯、横移（若限位允许）和转向切换误差；标定轮径、轮位、转向零偏和滑移协方差。
- 阶段一由 `agri_base_adapter` 实现带时间戳的速度仲裁、限速、超时归零和锁车；
  后续任务管理器通过 `/base_motion/set_lock` 屏蔽导航/遥控速度源，取消活动导航目标
  并保持最终出口零速。仅当 `|v| < 0.01 m/s`、`|w| < 0.02 rad/s` 持续 0.5 s
  后才允许机械臂离开收纳位。
- 机械臂运动期间若底盘速度再次越过阈值，应立即停止机械臂并进入安全恢复。标准验收不得用“把底盘固定到世界”的约束掩盖重心或抗倾覆问题。

### 8.3 MID-360、建图与导航

- Gazebo 中用 `gpu_lidar` 建立 360° x 59° 的等效 3D 传感器，加入量程、噪声和典型 10 Hz 更新率。
- 通过 `ros_gz_bridge` 将 `gz.msgs.PointCloudPacked` 单向桥接为 `sensor_msgs/msg/PointCloud2`。Jazzy 不采用被忽略构建的 `ros_gz_point_cloud` 包。
- `agri_lidar_adapter` 将 `mid360_sensor_frame` 点云按时间戳 TF 变换到同光心的水平
  `mid360_scan_frame`，再按导航高度/量程、自体盒和可选体素规则过滤；复用 Jazzy
  `pointcloud_to_laserscan` 发布 `/scan`。默认切片为 `-0.40..0.40 m`、量程
  `0.10..40 m`、角分辨率 1°，实际范围须按地面、底盘、茎秆和行末结构调参。
- 建图使用 SLAM Toolbox；正式导航使用保存地图 + AMCL，避免每次演示都在线建图。
- 全局代价地图使用静态层和障碍层，局部代价地图可使用 voxel/障碍层；footprint 必须覆盖导航时机械臂收纳状态的整机外接多边形。
- 参照 `ysftzc/robot_workspaces` 的导航框架，首版使用 NavFn（Dijkstra）+ Regulated Pure Pursuit（RPP）；按本项目四舵轮能力重新配置速度、转弯、footprint 和恢复。建图采用 SLAM Toolbox，定位采用 AMCL，不接入 FAST-LIO；开发流程见 `docs/navigation_development_plan.md`。
- 温室平行结构高度重复，需依靠可靠轮速里程计、IMU、行末结构和回环约束，避免定位跳变。

### 8.4 D405 与 YOLOv8 三维识别

推荐使用 `YOLOv8n-seg` 建立首版，因为实例掩码比矩形框中心更适合处理叶片遮挡和相邻果实。性能不足时使用 TensorRT/ONNX 优化，精度不足时再升级到 `yolov8s-seg`。

单帧处理流程：

1. 使用近似时间同步获取彩色图、对齐深度图和 CameraInfo。
2. YOLOv8 输出成熟度类别、置信度和实例掩码。
3. 腐蚀掩码以移除边缘混合像素，在掩码内部取有效深度中位数并做离群值剔除，作为粗定位和质量检查。
4. 使用 CameraInfo 将掩码内有效深度像素反投影为局部点云，通过稳健球体拟合或聚类质心估计果心和半径，并从可见表面拟合法向；不能只把单个中值深度像素当成果心。
5. 使用图像时间戳查询 TF，将果心、表面法向和协方差转换到当前 `base_link`；完成 Xacro 语义化后再提供 `arm_base_link` 别名。
6. 连续多帧聚类/跟踪，稳定后才发布可抓取目标；记录协方差或质量评分。
7. 抓取坐标系原点取果心，接近轴优先取可见表面外法向的反向；夹爪闭合轴与接近轴正交。围绕接近轴采样多个 roll，并按果实半径、指长和安全余量生成预抓取偏移。
8. 对姿态候选依次做工作空间、IK 和碰撞过滤，再按成熟度、置信度、遮挡、运动代价和已采摘目标距离排序。

D405 官方标注的 [Ideal Range 为 7-50 cm](https://www.realsenseai.com/products/stereo-depth-camera-d405/)，适合作为近距抓取定位基线。仿真允许通过 `d405_extended_sim.yaml` 将理想深度量程扩展至 2 m，用于后续 YOLO 检测和目标粗定位流程；感知距离过滤需随配置参数化。搜索策略为：Nav2 到达行间扫描站点，CR5 扫描并粗定位，再接近至 0.10-0.50 m 重新估计抓取位姿。2 m 仿真量程不承诺实机 D405 的远距精度或深度有效率；实机远距搜索需求需按现场验证选择传感器。YOLO 流程仍待实现。

训练数据应包含 Gazebo 合成图与真实温室图的预留接口。离线数据生成器可以读取 Gazebo 语义真值产生 YOLO segmentation 标签，但必须与运行时感知节点和 Topic 隔离。合成数据至少随机化光照、叶片遮挡、果实大小/颜色、相机姿态、纹理和背景。

首版数据基线为训练集不少于 3000 张、验证集不少于 500 张、测试集不少于 500 张；按世界布局和随机种子划分，禁止把同一连续序列拆到不同集合。`dataset.yaml` 记录类别和路径，`manifest.json` 记录场景、随机种子、生成参数及每个文件的 SHA-256。初始推理阈值为 confidence 0.50、NMS IoU 0.50，最终阈值在验证集确定后冻结，测试集不得用于调参。

### 8.5 CR5、夹爪和 MoveIt 2

- 以官方 CR5 模型和手册校验关节轴、零位、限位、质量和网格，不直接假设 Humble 配置在 Jazzy 可用。
- 用 MoveIt Setup Assistant 建立 `agri_robot_moveit_config`，规划组至少包含 `cr5_arm` 和 `gripper`。
- 使用 `JointTrajectoryController` 执行机械臂轨迹；两指夹爪优先使用 `parallel_gripper_action_controller/GripperActionController`，另一指可按实际连杆关系使用 mimic joint。
- MoveIt 轨迹执行只把 `cr5_arm` 映射到 `FollowJointTrajectory`；夹爪开合由任务管理器直接调用 `ParallelGripperCommand`，避免把它误配为 MoveIt 的旧 `GripperCommand` 控制器。
- 配置 SRDF 自碰撞矩阵、KDL/可选 IK 插件、关节限制、OMPL 和控制器映射。
- 底盘、篮筐和机械臂均属于 URDF RobotModel，只通过 SRDF 自碰撞矩阵管理，禁止再作为 world collision object 重复加入 PlanningScene。
- 基线方案不规划移动底盘自由度：MoveIt 以 `base_link` 为固定规划坐标，只在任务管理器确认底盘静止后规划。场景同步节点在每个扫描站点将土槽、棚架和简化植株从 `map` 转换到 `base_link`，清理旧对象后刷新 world collision objects。
- 抓取成功后，将对应番茄加入 attached collision object；释放后删除 attached object。Gazebo 内部附着状态和 MoveIt 碰撞状态必须由同一任务事务更新，失败时回滚。
- 预抓取可使用 OMPL；靠近果实的最后一段优先使用笛卡尔直线或 Pilz LIN，并限制速度和加速度。
- 固定篮筐中定义 `basket_drop_pose`。先移动到篮筐上方安全点，再打开夹爪，禁止直接规划到篮筐内部碰撞区域。

### 8.6 目标搜索、抓取和恢复

每个扫描站点执行：

1. 停车并锁定底盘。
2. 机械臂从收纳姿态移动到扫描姿态序列。
3. 聚合多帧检测，过滤已采摘和不可达目标。
4. 为目标生成多个候选抓取姿态并按可达性、碰撞和深度质量排序。
5. 规划到预抓取位，直线接近，闭合夹爪并附着目标。
6. 直线撤离，移动到篮筐上方，释放并确认番茄进入篮筐区域。
7. 更新目标状态；继续下一目标或收臂并导航到下一站点。

恢复策略：

- 检测丢失：回到观察位重新采集，最多 2 次。
- 深度无效：改变相机观察角度后重试，禁止用固定假深度抓取。
- IK/规划失败：尝试下一个候选抓取姿态；全部失败则标记不可达。
- 抓取失败：张开夹爪、撤回安全位并重新检测，最多 2 次。
- 导航失败：执行 Nav2 恢复；仍失败则跳过站点并记录原因。
- 任意严重异常：停止底盘和机械臂，保持或返回安全姿态并发布失败状态。

包边界原则：

- `ros2_ws` 不得依赖 `sim_ws`；`sim_ws` 可以在构建前 source `ros2_ws`。
- `agri_robot_description` 保存 canonical link/joint/TF；`agri_sim_description` 只追加 Gazebo 插件和传感器。
- `agri_bringup` 负责硬件无关组合，`agri_sim_bringup` 负责 Gazebo 专用启动。
- `agri_interfaces` 只存稳定通信契约，避免算法包循环依赖。
- 所有我方应用节点使用 Python 3.12、`rclpy` 和 `ament_python`。
- Gazebo entity ID、真值位姿和仿真专用 Topic 不得进入 `ros2_ws` 算法接口。
- 仿真和实机通过相同 Topic/Action 接口切换，算法包不感知硬件来源。
- 本阶段不创建 `references/`。
- 两个工作空间各自的 `build/`、`install/`、`log/`、缓存、rosbag 和训练输出不提交 Git。

## 11. 测试与验收计划

### 11.1 测试层级

| 层级 | 测试内容 | 工具 |
| --- | --- | --- |
| 静态检查 | URDF、Xacro、YAML、lint、许可证 | `check_urdf`、ament lint |
| 单元测试 | 四舵轮运动学、坐标转换、深度统计、目标排序、状态机分支 | pytest |
| 组件测试 | 控制器 action、传感器频率、TF 连通、点云转换 | `launch_testing`、rosbag2 |
| 子系统测试 | 建图导航、视觉定位、机械臂抓放 | 固定世界和固定随机种子 |
| 系统测试 | 多站点完整采摘任务 | Headless Gazebo + 指标脚本 |

### 11.2 必测场景

- 空道路直行、转向、狭窄行间会车/绕障。
- 地图初始位姿正确与轻微偏差两种定位情况。
- 单个清晰番茄、多个相邻番茄、叶片部分遮挡、无成熟番茄。
- 无效深度、目标越界、MoveIt 无解、抓取丢失、导航失败。
- 不同光照、材质、传感器噪声和至少 10 个固定随机种子。
- 篮筐为空和已有若干番茄两种放置场景。

### 11.3 记录指标

- 导航成功率、路径长度、耗时、最小障碍距离和恢复次数。
- 检测 Precision/Recall/mAP、推理延迟和有效深度比例。
- 三维定位误差、规划成功率、抓取成功率和入篮成功率。
- 端到端任务成功率、平均单果耗时和各阶段失败原因。
- Gazebo real-time factor、CPU/GPU/内存占用和话题频率。

在机械限位与稳定性确认前属于条件能力。

## 12. 主要风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Dobot 官方工程基于 Humble/Gazebo Classic | Jazzy 编译或控制不兼容 | 只复用经许可的模型/参数，重新生成 Jazzy MoveIt 2 与 `gz_ros2_control` 配置 |
| Livox 官方仿真插件不支持 Harmonic | 无法直接复刻扫描模式 | 首版采用标准 GPU LiDAR；封装相同 PointCloud2 接口，后续再开发非重复扫描插件 |
| CAD 网格过大或惯性错误 | 仿真卡顿、抖动、穿模 | 简化碰撞网格，校核单位、质量、质心和惯性 |
| 四舵轮机械限位和零位未知 | 横移/原地旋转不可用，里程计误差增大 | M0 确认转向限位、零位、减速比和反馈方向；未确认前只验收直行与小角度转弯 |
| 温室结构重复 | SLAM/AMCL 错配和跳变 | 融合里程计/IMU、保留行末特征、限制错误回环并回放调参 |
| D405 距离短、叶片遮挡 | 无法远距离搜索、深度空洞 | 使用站点+机械臂扫描，多视角融合；需要远距搜索时增加广角相机 |
| 只用 2D 框中心取深度 | 深度落到背景或叶片 | 使用实例掩码、腐蚀、有效深度中位数和多帧一致性 |
| 机械臂与底盘同时运动 | 定位误差和碰撞风险 | 任务级互锁；抓取时底盘必须静止 |
| 纯接触物理抓取不稳定 | 端到端测试随机失败 | 首版使用判定后附着模型，物理抓取作为增强项 |
| 仿真到真实域差异 | 实机识别率下降 | 域随机化、真实数据微调和分层实机标定 |
| YOLOv8 许可证不适配交付模式 | 闭源/商业发布风险 | 项目启动时确认 AGPL-3.0 合规或采购企业许可 |

## 14. 开发环境安装（Ubuntu 24.04）

以下仅作为项目环境基线。优先参考官方文档；不要同时安装 Gazebo Classic 和不匹配的 Gazebo Sim 版本。

### 14.1 ROS 2 Jazzy

按照 ROS 2 Jazzy 官方 Ubuntu deb 安装流程配置软件源后执行：

```bash
sudo apt update
sudo apt install ros-jazzy-desktop ros-dev-tools python3-colcon-common-extensions python3-vcstool
```

加载环境：

```bash
source /opt/ros/jazzy/setup.bash
```

建议先在当前终端验证，再决定是否写入 `~/.bashrc`。不要在同一终端加载多个 ROS 发行版。

初始化 rosdep：

```bash
sudo rosdep init
rosdep update
```

若系统已初始化，`sudo rosdep init` 提示配置已存在属于正常情况。

### 14.2 Gazebo Harmonic 与核心 ROS 包

Jazzy 通过 ROS vendor packages 提供官方匹配的 Gazebo Harmonic，安装 `ros_gz` 即可，不必额外添加 OSRF 软件源：

```bash
sudo apt update
sudo apt install \
  ros-jazzy-ros-gz \
  ros-jazzy-gz-ros2-control \
  ros-jazzy-ros2-control \
  ros-jazzy-ros2-controllers \
  ros-jazzy-parallel-gripper-controller \
  ros-jazzy-robot-state-publisher \
  ros-jazzy-twist-mux \
  ros-jazzy-navigation2 \
  ros-jazzy-nav2-bringup \
  ros-jazzy-slam-toolbox \
  ros-jazzy-robot-localization \
  ros-jazzy-pointcloud-to-laserscan \
  ros-jazzy-moveit \
  ros-jazzy-xacro \
  ros-jazzy-tf2-tools \
  ros-jazzy-cv-bridge \
  ros-jazzy-depth-image-proc \
  ros-jazzy-image-geometry \
  ros-jazzy-image-transport-plugins \
  ros-jazzy-rqt-image-view
```

最终依赖以各 ROS 包的 `package.xml` 为准，在工作空间根目录执行：

```bash
rosdep install --from-paths src --ignore-src --rosdistro jazzy -r -y
```

验证版本和基础程序：

```bash
echo "$ROS_DISTRO"
gz sim --version
rviz2
```

启动 Gazebo 空世界：

```bash
ros2 launch ros_gz_sim gz_sim.launch.py gz_args:="-r empty.sdf"
```

现代 Gazebo 本身不保证出现名为 `/gazebo` 的 ROS 节点。应通过 `gz topic -l` 检查 Gazebo Transport，通过 `ros2 topic list` 检查已配置的 ROS bridge。

### 14.3 Python 视觉环境

不要直接把未经锁定的 pip 包安装到系统 Python。建议在工作空间使用可访问 ROS 系统包的虚拟环境：

```bash
python3 -m venv --system-site-packages .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

`requirements.txt` 应锁定 Ultralytics、PyTorch、OpenCV 辅助包等版本。PyTorch/CUDA 安装命令必须按开发机显卡和官方兼容矩阵选择，不在需求文档中写死。

### 14.4 构建与验证

```bash
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install
source install/setup.bash
colcon test --event-handlers console_direct+
colcon test-result --verbose
```
